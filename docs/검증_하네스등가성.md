# 검증 — 통합 하네스가 당시 하네스와 같은 실험을 만드는가

## 1. 왜 필요한가

실험은 스텝마다 따로 진행됐고, 그때마다 하네스(실험 엔진)가 조금씩 달랐다.
step1부터 step5까지 다섯 갈래로 갈렸고, `src/harness`의 파일이 **전부** 서로 달랐다.

나중에 이것들을 하나로 합쳤다. 지금 저장소의 `src/harness`가 그 통합본이다.
그러자 당연한 의문이 생긴다.

> 코드를 고쳤는데 결과가 달라지는 것 아닌가?

이 문서는 그 질문에 답한다. 답하는 방식은 **같은 조건에서 같은 실험 입력이 나오는지를
문자 단위로 비교하는 것**이다.

---

## 2. 무엇을 비교하나

결과 JSON 하나하나에는 그 결과를 만든 **조건**이 들어 있다. 그 조건을 옛 하네스와
지금 하네스에 각각 넣어 실험 입력을 생성하고, 해시를 떠서 비교한다.

| 비교 항목 | 무엇 |
|---|---|
| `slug` | 결과 파일 이름 |
| `instruction` | 지침 문장 원문 |
| `preceding` | 선행 코드 12개 원문 |
| `viol_messages` · `comp_messages` | 개입 실험의 프롬프트 전문 |
| `viol_names` · `donor_names` | 치환 대상과 공여 위치의 이름 |
| `donor_messages` | 공여 프롬프트 |
| `cands` | 두 후보 함수 이름 |

즉 **모델에 들어가는 것과 개입이 일어나는 자리**를 전부 비교한다. 하나라도 다르면
실패로 처리한다.

---

## 3. 돌리는 법

```bash
bash scripts/verify_harness_equivalence.sh
```

torch·numpy·pytest 없이 순수 파이썬으로 돈다. GPU도 네트워크도 필요 없다.

### 결과

```
  step1_cliff: 일치
  step2_code-observe: 일치
  step3_code-cause: 일치
  step4_instr-observe: 일치
  step5_instr-cause: 일치
전부 일치 — 통합 하네스로 다시 돌려도 같은 실험이 된다
```

---

## 4. 옛 하네스는 어디에 있나

`scripts/harness_snapshots/` 안에 파일로 들어 있다.

| 폴더 | 원래 브랜치 |
|---|---|
| `step1_cliff/` | `step1/cliff` |
| `step2_code-observe/` | `step2/code-observe` |
| `step3_code-cause/` | `step3/code-cause` |
| `step4_instr-observe/` | `step4/instr-observe` |
| `step5_instr-cause/` | `step5/instr-cause` |

각 폴더의 `COMMIT` 파일에 원본 커밋 SHA가 들어 있다.

예전에는 이 검증이 브랜치를 `git archive`로 꺼내 썼다. 브랜치를 `main` 하나로 정리하면서
**파일로 박제**했다. 이제 저장소 하나만 있으면 검증이 끝나며, 네트워크도 다른 브랜치도
필요 없다. 원본 브랜치들은 `local/*`·`exp/*` 태그로도 보존돼 있다.

---

## 5. 이것이 보이는 것과 보이지 않는 것

**보이는 것.** 통합 하네스가 각 실험 당시와 **완전히 같은 프롬프트·치환 대상·후보·파일명**을
만든다. 코드를 합치는 과정에서 실험 설계가 바뀌지 않았다.

**보이지 않는 것.** 같은 숫자가 나온다는 증명은 아니다. 그것은 같은 모델을 같은 환경에서
다시 돌려야 알 수 있다. 다만 입력이 같고 시드가 고정(42)이고 temperature가 0이므로,
같은 환경이라면 같은 값이 나올 것으로 기대한다.

**남은 불확실성.** 결과 3,528개에 실행 환경 기록(`meta`)이 없고, 기록이 있는 것도 대부분
`git_dirty: true`다. 자세한 내용은 [`환경_및_버전.md`](환경_및_버전.md) §2에 있다.
이 검증은 **코드가 만드는 입력**이 같음을 보일 뿐, 실행 당시 커밋되지 않은 수정이
있었는지까지는 답하지 못한다.
